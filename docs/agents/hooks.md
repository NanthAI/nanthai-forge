# Installed agent hooks

Rule: **a hook guards or informs about the action happening now (this edit, this stop).** Anything that arrives later (board notes, notices, messages) rides on command replies and on `wait`, never on a hook. Every hook costs zero while idle and fails open.

`nforge` installs hooks for Claude Code (`~/.claude/settings.json`) and Codex (`~/.codex/hooks.json`) on the first run of an installed CLI, and `nforge connect antigravity` installs Antigravity's hook (`~/.gemini/config/hooks.json`). Any legacy Forge `UserPromptSubmit` entry is stripped on install and never added.

## Hook state on an agent run

The project's agent run page shows the latest Forge hook state the CLI reported on a Lane start or save sent to
Forge. **Off** reflects Forge's local user or project switch, Claude Code's user setting `disableAllHooks`, or
Codex's user setting `features.hooks`. **Configured** means the CLI found a working hook target for that agent
app. Its report describes local configuration. **Unavailable** means the CLI could not confirm a working target.
Older clients leave the state unreported. The report includes the time of the action and uses the existing request.

With first-write hooks off, edits lose the clone-root guard, the overlap and claim notices for the edited path,
automatic touching claims, and the warnings about unsaved work and in-flight landings. Disabling hooks for the
whole user also turns off the stop guard and its turn-end snapshot on clients that support them. Uninstalling
Forge's hooks also removes the Claude Code deny rules that Forge added. Forge commands still deliver board notes
and report saved overlap.

## Known gaps and client limitations

- **Codex `Stop` hook live verification:** tracked in Item `2f13b3cf` (see [turn-end guard](workflow.d/sections/2400-turn-end-guard.md)).
- **Antigravity `Stop` hook live verification (Item `d0e9ce11`):** `nforge connect antigravity` installs `Stop` under `forge-first-write` in `~/.gemini/config/hooks.json` (`agent-antigravity-hook.js --forge-turn-end`), translating a first-stop block to Antigravity's `{"decision":"continue","reason":"…"}` and failing open (`{}`) on errors or non-normal `terminationReason` values. Because Antigravity does not document a per-conversation shell environment variable matching hook `conversationId`, the hook checks `conversationId` first and falls back to the Forge session key (`T3CODE_THREAD_ID` or the `antigravity`/`agy` ancestor process key) when no `FORGE_AGENT_SESSION` override is set. Verified with unit and child-process tests; not yet observed end-to-end in a live `agy` session on this host.
- **Codex secret-file read deny rules (Item `d0e9ce11`):** not auto-installed because Codex has no fail-open, non-overriding read-tool deny rule:
  - Codex has no built-in `Read` tool (files are read through shell commands under `Bash`/`exec_command`), and `~/.codex/hooks.json` has no `permissions.deny` schema.
  - Declarative filesystem deny rules in `~/.codex/config.toml` (`[permissions.<name>.filesystem]`, Beta) cannot be layered safely onto a user's config: activating a profile requires setting top-level `default_permissions`, which is mutually exclusive with `sandbox_mode`/`--sandbox` (silently ignored when `sandbox_mode` is set anywhere), would override a user's existing `default_permissions` profile (such as `:read-only`), and fails closed on hosts where the sandbox cannot enforce the profile. Tested on `codex-cli 0.170.0` with `codex sandbox --permission-profile` against scratch dummy files (`**/.env* = "deny"`, `**/*.pem = "deny"` blocked `cat` while allowing normal files), so users who already manage their own Codex permission profile can add those deny entries manually.
  - Codex Starlark `.rules` (`prefix_rule`) only govern commands requesting execution outside the sandbox by command prefix, not sandboxed file reads or path globs.
  - Intercepting every `Bash` call in `PreToolUse` with shell-string regexes cannot reliably distinguish secret reads from harmless references (docs, tests, `nforge` reading its own auth file) and invalidates Codex's per-hook trust hash.
- **Antigravity secret-file read deny rules (Item `d0e9ce11`):** not auto-installed because Antigravity exposes neither a safe `PreToolUse` pass-through across versions nor cross-surface glob read-deny rules:
  - In bundled `agy-customizations/docs/hooks.md` and live tests on `agy -p` / `agy acp` (CLI 1.5.13, Issue `c6615b66`), `PreToolUse` requires `decision`: `{}` denies the tool (fails closed) and `"decision": "allow"` auto-approves past the user's permission rules. Even though newer web docs (`antigravity.google/docs/hooks.md`) distinguish `"allow"` from `"auto_approve"`, installing a `PreToolUse` read hook would bypass user permission rules on existing CLI/ACP versions or fail closed on empty/error replies.
  - Antigravity's `permissions.deny` JSON (`~/.gemini/antigravity-cli/settings.json`) applies only to Antigravity CLI (`agy`)—not Antigravity App, IDE, or ACP—and its `read_file(...)` target format (`read_file(/path)`, `read_file(dir)`, `read_file(*)`) matches exact/prefix paths or global `*`, not filename/extension globs such as `**/*.pem`, `**/*.key`, or `**/.env*` (unparseable rules are silently ignored by the CLI).
