## Model after V1

**Candidate.** The first-class, pinned proposal reviewed, checked and landed: base State, ordered saved Lane heads, dependencies, resulting State or explicit source conflicts, and provenance. An Intent can have several Candidates; edits or recomposition produce a different Candidate. Runs and acceptance receipts retain the exact identity. A Candidate has submission outcomes; it is not a mutable workspace or a promise that every input will land.

**Lane.** A contributor's workspace: directory/materialization, saved source pins, presence, scope and association with an Intent. Hosted Lane records are authoritative for hosted source; local files and caches are materializations. A Lane can contribute to several Candidates. Presentation derives “checking”, “landed” or “needs fix” from its selected submission/evidence; retained legacy lifecycle fields remain compatibility data. Closing/reopening a workspace stays available and never erases saves or rewrites a submitted Candidate.

**Intent.** The intended outcome and its constraints, context, owner decisions and proving-test contract. Multiple Lanes may implement it and multiple Candidates may attempt it. Completion describes the outcome, not mere directory closure. A versioned test contract is a declaration with exact measurement pins; it is distinct from an exported API/schema contract and from permission to use a reduced gate.

**Channel.** A named pointer to accepted source with immutable acceptance receipts. `main` advances through current authority, exact source/evidence and head/receipt concurrency checks. “Landed” requires that receipt. An accepted contract-gated Candidate may later need repair; accepted does not mean that the asynchronous full audit passed.

**State.** Immutable source bytes, file modes and ancestry identified by a digest. Saves and composition create States; a Candidate adds intent/input provenance to source identity. State stays available in exact records and source selection without making agents manage storage machinery on the ordinary path.

**Check.** A versioned command definition; a run pins Candidate, selection, definition, configuration/environment and outcome. The effective gate is `full` or eligible `contract`, following current policy, actor and changed paths; the contract gate includes declared tests, changed tests and the composed Intent union. Supervised, contributor, protected/unknown-path, contract-less and system cases retain their existing full/review rules. Missing gate keeps full; naming consolidation changes none of these rules.

**Decision.** An attributed, immutable owner/authorized-maintainer choice with reason, target, overridden default/decision and replacement links. It supplies context; recording “enable contract gate” does not enable it, change policy or grant authority. V1's decision remains proposed until the owner agrees.

**Friction.** A structured observation of workflow trouble and known cost, linked to evidence and a fixing Lane. Triage and recurrence guide work; they neither establish causation nor authorize restrictions. Preserve original attribution, operation IDs and history across native/hosted routing.

Remove **View** from teaching and ordinary labels (Candidate aliases already exist); retain persisted `viewId`, `views`, `kind:view` and historical URLs. Say **save**, not checkpoint, in the normal loop; retain checkpoint/State identities in exact records. Retire “finish”, “land-ready” and “complete-merged” as ordinary lifecycle vocabulary. “Run”, “submission”, “batch” and “receipt” remain precise evidence terms, rather than additional work objects agents must create by hand.

A GitHub PR is the closest analogy to a Candidate plus Intent context; a branch/worktree approximates a Lane; the merge queue approximates batched submissions. Forge permits multiple Lanes per Intent, exact composed proposals across Intents and immutable dependency pins. It does not require a Git branch, PR number, rebase or history rewrite. A batch is an execution/landing optimization containing ordered Candidate inputs, not a new authored proposal or an all-or-nothing guarantee.

Culprit notices must distinguish an observed failed combination from an attributed culprit and from infrastructure/flake/unknown results. A recovery notice carries audit/run and accepted-head/receipt pins, `reverted` or `needs-fix`, failed tests, retained Lane/repair Intent and the exact undo action. Preparation of a revert creates a compensating Lane; only its acceptance receipt means it landed. Preserve current versus historical applicability and `needsFix`/`fixBrief` delivery; never turn missing evidence into blame or require a new acknowledgement.

2. **Hosted/MCP and operator homes (Phase 5, M):** update `mcp-agent-workflow.ts`, `mcp-hosted-agent.ts`, `mcp-agent-wait.ts`, `mcp.ts`, `hosted-agent-contract.ts` adapters and `cli.ts` dispatch/help; add `x` routing to existing handlers without changing permissions or execution. 3. **Teaching and validation (Phase 5, S):** update README, AGENTS, packaged `skills/forge-agent/SKILL.md`, `docs/quickstart.md`, concepts, agent workflow and MCP descriptions to teach start/save/land; status docs only if an implemented capability changes. 4. **Tests:** every mapping row, every grouped variant and every new surface mode gets a table-driven test through CLI and the applicable MCP/hosted boundary, plus a registry-coverage assertion so new actions cannot escape the inventory. Extend `agent-action-parse`, `agent-cli-mcp`, `candidate-names`, `land-command`, `hosted-agent-cli`, `hosted-agent-mcp`, `hosted-agent-capabilities`, `hosted-agent-transport`, `hosted-records-transport`, `hosted-check-configure`, `work-format-compatibility` and schema-compat tests; run impact selection and all changed-module importers, then full verify. 5. **Behavior cases:** old/new invocation returns the same State/Candidate/run/submission/receipt and one operation count; lost reply/reconnect; same-ID changed-payload rejection; check-only; saved-head versus dirty workspace; multilanes/stacks; main head and receipt races; partial batch success; supervised/person/contributor distinctions; contract escalation and red-main waits; flake/culprit/revert notices with undo; contract confirmation measurements; finite wait cancellation; paged decisions/metrics and answer batches; unsupported mode and failed capabilities never write native Work.
6. **Skew:** old CLI/new server continues schema-1 names, accepted inputs, errors and strict response shapes. Released clients parse capabilities strictly: do not append `land`, operator, owner or record names to their enum, nor silently rename/remove an action. Replay selects original semantic version and authority epoch; deployment never rewrites pending journals, Work formats or historical identifiers. Keep aliases at least one release; removal requires a separately approved version boundary and client evidence.

## Recommendation, cost and measurement

Ship **V2a in Phase 5**: roughly two medium adapter slices plus a small teaching/test slice. It removes lifecycle spelling choices without removing recovery capability, but three verbs still have explicit modes; do not claim three total operations. Preserve named reads for this release. Alias support costs parser/help/compatibility fixtures, not new queue engines or hosted record migrations.

Move **V2b to Phase 6**. Alias removal and read consolidation change discovery and old prompts; a released compatibility cycle and usage/error evidence should come first. Medium cost: versioned read schemas, cursor/pin preservation, migration docs and released-client fixtures. The uplift is fewer lookup choices; removing aliases alone does not prove fewer lifecycle errors. Keep a legacy protocol endpoint for supported old clients; do not strand pending work.

Move **V3 to Phase 6**, after the shared adapter semantics settle. Medium cost: generate CLI argument/help/discovery adapters from typed MCP descriptors with explicit mode/authority/side-effect metadata, plus hand-written byte-output, auth, clone and process entry adapters. Today registries differ by mode and contain grouped actions and writes inside overview tools; blindly generating from tool names would preserve drift. Require exact CLI↔MCP action/argument drift tests, not generated duplicate business logic.

Primary target: metric **5.2 (metric 2)**, agent-visible lifecycle errors per 100 unique finishes; secondary 5.5 interventions/landing. Current baseline rates are unknown, and after this memo remain unknown: design alone changes no runtime result.
